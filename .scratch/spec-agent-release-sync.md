## Problem Statement

GitHub 已发布 Agent 1.8.3 及 Windows x64、Linux x64、macOS ARM64 安装包，但本地平台下载页仍显示 1.8.2。用户无法确定哪里可以获得最新版本，也不应在每次发布后手动修改平台代码中的版本号、文件名和下载链接。

当前平台只读取本地发布记录。记录为空或读取失败时，使用写死的 1.8.2 清单；修改源码版本、上传 GitHub Release 不会自动更新本地记录。CI 的主动登记依赖平台地址、令牌以及目标平台可达，不能保证本地开发平台收到登记。尚未核验 CI 的实际 Secrets 或登记日志，不把缺少密钥当作已证实原因。

页面展示的是“Agent 发布版本”，与每台设备的“Agent 运行版本”不同。同步下载信息不能被呈现为设备已经完成升级。

## Solution

平台自动获取本项目 GitHub 最新正式 Agent 发布及其清单，验证通过后统一更新下载页和客户端版本查询结果。同步版本号、发布日期、更新说明、安装包文件名、大小、下载链接和 SHA256，用户无需修改平台代码或依赖 CI 回调到本机。

使用短期缓存控制请求频率。网络故障、限流或发布清单不完整时继续提供最近一次有效发布，提示同步状态；首次没有有效发布时显示“尚未同步”，不伪造版本或下载链接。下载页提供手动刷新入口。

自动同步在平台处理发布信息读取请求时触发，无访问期间不承诺后台定时同步。已有 CI 发布登记保留，通过同一校验与持久化流程写入数据。

## User Stories

1. 作为下载 Agent 的用户，我希望页面自动显示 GitHub 已成功发布的版本，以便获取实际可下载的新版本。
2. 作为本地平台使用者，我希望无需让 GitHub Actions 访问本机也能同步发布，以便本地部署正常使用。
3. 作为平台维护者，我希望发布后不用手改页面版本号，以便减少遗漏。
4. 作为下载用户，我希望版本、日期、说明和安装包属于同一次发布，以便判断下载内容。
5. 作为 Windows x64 用户，我希望获得对应安装包，以便在设备上运行。
6. 作为 Linux x64 用户，我希望获得对应安装包，以便在设备上运行。
7. 作为 macOS ARM64 用户，我希望获得对应安装包，以便在 Apple Silicon 设备上运行。
8. 作为其他架构用户，我希望明确得知没有匹配的安装包，以免下载错误文件。
9. 作为下载用户，我希望看到准确的文件大小与 SHA256，以便判断下载及校验结果。
10. 作为下载用户，我希望链接固定指向展示版本的文件，以免 GitHub 最新版本变化导致链接失效或内容混用。
11. 作为下载用户，我希望在首次同步时看到加载状态，以便知道平台正在获取发布信息。
12. 作为下载用户，我希望首次同步失败时看到“尚未同步”和可重试提示，以免误把默认值当成最新版。
13. 作为下载用户，我希望网络异常时仍能查看最近一次有效发布，以便继续使用已知的下载信息。
14. 作为下载用户，我希望区分“已同步”和“同步失败，使用已缓存版本”，以便判断信息的新鲜程度。
15. 作为下载用户，我希望主动刷新发布信息并得到成功、无变化或失败反馈，以便确认新发布是否可用。
16. 作为平台维护者，我希望重复访问及多个客户端查询共享缓存和进行中的同步，以便减少 GitHub 限流。
17. 作为平台维护者，我希望平台重启后保留有效发布记录，以便 GitHub 临时不可达时不丢失信息。
18. 作为平台维护者，我希望不完整或不一致的清单不替换有效版本，以免用户获得损坏的下载信息。
19. 作为平台维护者，我希望预发布、草稿及非 Agent 发布不进入稳定版下载页，以免错误推送测试版本。
20. 作为平台维护者，我希望重复同步同一发布不会产生重复记录，以便发布状态保持一致。
21. 作为平台维护者，我希望 CI 登记和自动同步同时发生时不会回退到旧版本，以便用户稳定获取新版。
22. 作为 Agent 使用者，我希望版本接口与下载页使用同一份有效清单，以免两处对最新版的判断不同。
23. 作为 Agent 使用者，我希望没有有效发布时版本接口明确返回不可用，以免触发错误升级。
24. 作为设备管理员，我希望同步发布信息不改变设备的 Agent 运行版本，以便真实掌握安装情况。
25. 作为平台维护者，我希望同步失败有简明原因和时间信息，以便区分网络、清单与存储问题。

## Implementation Decisions

- **统一入口**：扩展现有 Agent 发布读取服务，集中负责读取缓存、同步、验证、保存和返回状态。平台快照、下载页、版本查询及升级决策均消费它，不各自访问 GitHub。
- **来源与候选发布**：默认源为 `upengfei/playmate-automator` 的 GitHub Releases。仅接受 `agent-v` 加稳定三段数字版本号的正式发布；排除草稿和预发布。若 GitHub latest 为其他类型发布，再从有界分页列表中选取最新正式 Agent 发布；请求必须有数量和时间上限。
- **以清单作为发布完成条件**：读取候选发布附带的 `agent-release.json`，与该次 Release 的资产列表交叉验证。不从源码版本生成假清单，不因获取了 Release 元数据就认定发布可用。最新候选未就绪时保留已有有效发布；空库则提示未就绪，等待重试。
- **清单校验**：清单版本须与标签一致；文件名中版本、平台和架构须与声明一致；文件不得重复。当前正式交付矩阵为 Windows x64、Linux x64、macOS ARM64，三个目标均须有对应的已上传非空资产。SHA256 必须为 64 位十六进制串；若资产元数据提供摘要，还须匹配。此处校验清单及发布元数据，不下载全部大体积安装包；Agent 下载后仍执行文件内容校验。
- **资产地址与大小**：以同次 Release 的精确资产下载 URL 和字节大小生成链接与展示大小，链接固定到该版本标签，不使用可变的 latest 前缀拼接旧文件名。清单若提供 URL，必须与同次发布资产相符。元数据仅从配置的 GitHub 仓库读取，不开放由浏览器任意指定上游地址的能力。
- **元数据补全**：当前 CI 清单可能只有 version 与 artifacts；发布日期取 GitHub published_at，channel 默认为稳定版，更新说明优先使用清单 notes，否则展示同次 Release 的正文或明确的无说明状态。minSupported 缺失时沿用已有明确的兼容性要求；没有要求时保持现有无额外限制语义，不推导出新的强制升级门槛。
- **缓存与触发**：建议默认有效期 5 分钟。首次无缓存的读取等待一次有时限的同步；有有效记录时先返回记录，过期后触发共享的后台同步，由后续平台快照刷新显示结果。单次同步总时限默认 20 秒，失败后至少 60 秒内避免自动重试风暴；常量或服务端配置集中管理，测试使用可控时间。
- **手动刷新**：下载页刷新动作可绕过有效期，但复用正在进行的请求，并遵守最短 60 秒重试间隔及上游 Retry-After。按钮显示进行中状态，结果区分有新版、版本未变化、刷新失败以及需稍后重试。服务端执行刷新，沿用平台现有访问边界，不把 CI 发布令牌交给浏览器。
- **持久化与一致性**：复用发布记录存储，校验全部通过后才以原子操作切换当前发布。版本唯一且同步幂等；旧请求晚到不得覆盖更高版本。CI 登记也使用同一切换规则。失败不能先清除当前标记，存储提交失败不能报告同步成功。
- **相同版本变化**：同版本、同一组资产身份及摘要视为重复同步；若同版本安装包身份或摘要变化，拒绝静默替换并提示发布不一致，需要发布新版本。本功能不为覆盖既有同版本二进制提供自动信任路径。
- **已有记录兼容**：结构有效的现有数据库记录可作为最近一次有效发布使用；保留既有文件名识别平台和架构的兼容能力。新同步数据必须严格校验。内置 1.8.2 和前端初始化的 0.0.0 均不得作为真实发布展示或参与升级比较。
- **状态合同**：统一发布读取结果允许 release 为空，附带同步状态、最近尝试时间、最近成功时间及用户可读原因。区分未同步、同步中、已同步和同步失败；同步失败可以同时附带上次有效 release。数据库读取异常且没有可用内存缓存时，也返回不可用状态而非硬编码版本。
- **公开版本接口兼容**：有有效发布时保留现有成功响应字段和平台/架构选包规则，新增同步状态字段；无匹配目标时 artifact 为 null，不回退其他平台。完全没有有效发布时返回 HTTP 503 和明确的 release_unavailable 错误，不返回占位版本。复核当前 Agent 对非成功响应的处理，确保不触发下载或误报已升级。
- **其他消费者适配**：平台快照、版本比较、升级下发等原先假定 release 必有值的消费者均须处理不可用状态；没有有效发布时不下发升级、不依据占位发布版本作最低版本判断，并给出简明提示，不影响用例等其他页面加载。管理员明确配置的任务最低版本准入规则独立于发布同步，继续生效；自动升级无法创建时明确返回“升级包不可用”，不误报已推送。本项在实施审查中澄清，避免网络故障意外解除既有的兼容性要求。
- **运行版本不变**：同步流程只管理 Agent 发布版本，不修改任何设备的 Agent 运行版本，也不修改本机应用、源码版本号或构建脚本中的版本号。

以上缓存时长、状态合同与一致性规则是依据已确认方案整理的实施默认值，并非声称用户逐项指定。测试边界的核对结果在下节记录。

## Testing Decisions

- **主要测试边界**：使用现有发布读取服务作为业务入口，执行真实校验和临时 SQLite 持久化，只替换 GitHub HTTP 与时间边界。尽量复用现有数据库参数和模块加载工具，不为每个内部函数建立独立 mock 接口。用户随后调用 implement，按该边界实施。
- **好测试的标准**：断言调用方最终看到的版本、文件、状态、错误及重启后的保留行为，不断言私有函数调用顺序、SQL 文本或组件源码片段。
- **先例**：项目已有 Node test runner；发布交付测试验证平台/架构选包和升级行为，平台数据测试使用临时 SQLite 并直接调用真实路由 handler，模块加载工具可替换外部依赖。沿用这些方式，测试不操作用户业务数据库、不依赖 GitHub 实时网络。
- **首次同步成功**：空库配合有效三平台发布，首次读取获得正确版本与精确标签下载 URL；再次读取及新服务实例读取能看到同一发布。
- **正常更新与不回退**：已有有效旧版本同步到新版；重复新版幂等；旧 CI 登记与慢速旧同步都不能回退新版。
- **并发与失败原子性**：多个请求同时读取时共享一次上游同步；保存过程故障后旧发布仍可读取，不出现空的当前发布或部分新清单。
- **缓存与重试**：有效期内不重复请求，过期读仍可立即取得已知发布，刷新完成后后续读取见新版；超时、限流和手动刷新都遵守约定的请求上限、重试间隔及反馈。
- **无有效数据与断网**：首次网络失败返回不可用；已有记录时断网仍返回旧版本及失败状态；不得出现硬编码 1.8.2 或占位 0.0.0。
- **不合格发布**：覆盖草稿、预发布、非 Agent 标签、无清单、无目标资产、版本冲突、重复文件、错误架构、非法摘要、错误 URL、同版本资产替换及畸形 JSON；已有有效记录不得被破坏。
- **版本接口合同**：通过现有路由 handler 验证有发布的兼容响应、无发布的 503、平台/架构匹配以及无匹配时 null。与平台快照抽样核对同一版本和资产，主业务逻辑仍由上述统一边界覆盖。
- **设备升级回归**：版本接口不可用时不下载；合法新版仍须校验下载内容；打开安装包仍处于等待安装状态，不把 Agent 发布版本写成 Agent 运行版本。
- **界面验收**：人工检查首次加载、空库失败、同步成功、缓存过期失败与手动刷新反馈；macOS ARM64 下载卡片和版本接口一致。默认不新增完整浏览器端到端自动测试体系。
- **交付检查**：实现后运行现有测试、类型检查和生产构建，并检查本次差异格式。仅在真实网络允许时补一次公开 Release 读取冒烟验证，结果与离线回归分开记录，不把网络失败冒充功能通过。

## Out of Scope

- 自动递增源码版本、创建标签、触发构建或发布 GitHub Release。
- 覆盖同名已发布安装包、重写 Git 或 Lovable 历史。
- 静默安装客户端、替换 macOS 应用、签名、公证或自动重启设备上的 Agent。
- 扩展新的操作系统/CPU 交付矩阵、灰度通道、预发布订阅或人工回滚机制。
- 改造全平台权限、任务调度、任务重试、用例录制或其他无关功能。
- 将本地业务数据库、凭据或运行时文件提交到 GitHub。
- 建立独立的常驻发布监控服务或在平台无访问时保证实时推送。
- 搭建下载镜像、代理所有安装包流量，或每次同步下载完整安装包进行服务端内容校验。
